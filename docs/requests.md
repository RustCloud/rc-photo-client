# Запросы к другим репозиториям

Что нужно приложению от плагина rc-photo (`RustCloud/rc-photo`), сервера (`RustCloud/server`) и
rc-client (`RustCloud/client`). Каждый запрос объясняет, зачем это нужно, что предлагается и как
приложение обходится, пока изменения нет. Когда изменение выйдет, ставим отметку с версией.

## 1. Дата изменения файла для фото без EXIF

**Где:** сервер (WIT плагинов) и плагин rc-photo. **Статус:** открыт (2026-11-22).

**Зачем.** Приложение при загрузке передаёт `?mtime=` — дату снимка с телефона. Сервер хранит её
в `Node.modified_at`. Но плагин в индексе пишет `Entry.modified = node.updated_at`
(`r-image/src/media.rs:134`, `:293`): это время загрузки на сервер. У файлов без даты в EXIF
(скриншоты, картинки из мессенджеров, часть видео) лента покажет их датой загрузки. Например,
при первой резервной копии все старые скриншоты окажутся в «сегодня».

Причина — у записи `node` в `wit/app.wit` (интерфейс `files`) нет `modified-at`, только
`updated-at`.

**Предложение.**

- Сервер: добавить `modified-at: string` (RFC 3339) в запись `node` интерфейса `files`
  (новая минорная версия WIT).
- Плагин: `Entry.modified = node.modified_at`, если есть, иначе `updated_at`. Уже
  проиндексированные файлы обновятся при `rebuild` или следующем изменении.

**Пока нет.** Для файлов, которые загрузило само приложение, дата берётся из его локальной базы.
Для остальных остаётся дата загрузки.

Проверено: `tools/api_check.py`, 300 фото загружены с `mtime` в 2024 году, `Entry.modified` —
время загрузки.

## 2. Версия API плагина и описание API

**Где:** плагин rc-photo. **Статус:** открыт (2026-11-22).

**Зачем.** Приложение выходит отдельно от плагина, и плагин на сервере может оказаться старее или
новее приложения. Приложению нужно знать, что умеет установленный плагин. А разработчикам
плагина — что поля, которые читает приложение, нельзя удалять или переименовывать молча.

Пример, на котором это уже сработало: по таблице в `api.rs` и коду страницы можно решить, что
`state.names` — это словарь «id человека → имя». На деле это вся структура `people::Names`
(`{names, hidden, merged, faces, covers, next}`), а имена лежат в `state.names.names`.

**Предложение (rc-photo 0.9.0, манифест не меняется, подтверждение администратора не нужно).**

- Поле `api: 1` в `GET /api/state` и маршрут `GET /api/version` → `{"version": "0.9.0", "api": 1}`.
- `docs/api.md` — описание API как договор с приложением:
  - все маршруты, включая те, которых нет в таблице в `src/api.rs`: `similar`, `text`, `stream`,
    `stories`, `upload-folder`;
  - форматы шардов: `index` (`Entry`), `texts`, `people`, `stories/<день>.json`;
  - ошибки;
  - правило совместимости: поля и маршруты только добавляются, удаление или переименование
    поднимает `api`.
- Тест в плагине сверяет примеры ответа `state` и `Entry` из `docs/api.md` с настоящими.
  Приложение использует те же примеры в своих тестах.

**Пока нет.** Приложение узнаёт возможности по наличию полей в `state` (`analysis`, `stories`,
`texts`, `people`) и по ответу `404` на маршрут. Если в `state` нет `shards`, показывает
«обновите плагин „Фото“».
